# 内存占用收敛 v1 产品规格

- 日期：2026-10-30
- 状态：待评审
- 关联：`docs/specs/v1-core/product.md`（扫描范围/增量契约）、`docs/specs/external-volumes/`、`docs/architecture.md` ADR-5（降级重扫）、ADR-2（内存索引）

## 1. 背景与问题

实机实测（2026-10-30，macOS 27.0，32GB，索引 1,259,610 条，index.bin 113MB，活动监视器口径 phys_footprint）：

| 指标 | 实测值 |
| --- | --- |
| daemon 稳态 footprint | 175–418MB 锯齿波动 |
| daemon 峰值 footprint | **784MB** |
| daemon 全量重扫频率 | 日志累计「转全量重扫兜底」507 次、「冷却拦截」8893 次 |
| daemon.log | 26.9 万行 / 26MB，96% 为「目录 diff 失败」刷屏 |
| GUI 稳态 footprint | 306MB（其中堆仅 49.7MB，图形栈为大头） |
| GUI 峰值 footprint | **1.7GB**（归因未定，见 tech.md §6） |

根因是三条互相咬合的链（详见 tech.md §0）：

1. **重扫振荡**：FSEvents dropped 标记 → 消费线程内同步全量重扫（10–30s 停摆）→ 内核缓冲溢出产生新 dropped → 30s 冷却后再次重扫，永不收敛。
2. **重扫峰值**：扫描中间表示逐条拷贝完整父路径 + 新旧索引并存，单次重扫峰值数百 MB；释放后 malloc 死页滞留不归还。
3. **永久失败目录无限重试**：`.Trash`（TCC 权限）失败 171,578 次、照片图库 11,144 次、已删目录（ENOENT）3.3 万次——每次白跑拖慢消费，加剧溢出；dropped 丢弃删除事件又使死条目永留索引，只有重扫能清理，系统在用最昂贵的方式「自愈」。

## 2. 已确认决策（2026-10-30）

| 决策 | 选择 | 备注 |
| --- | --- | --- |
| 目标口径 | **daemon 稳态 footprint ≤ 100MB（硬性）** | 目标值 60MB，留余量；活动监视器「内存」列同口径 |
| GUI | **阶段一 ≤ 150MB（确定性手段）；阶段二 ≤ 100MB（归因驱动探索）** | 评审否决了「技术栈下限 ~230MB」的初判：phys_footprint 不含 clean 库页，306MB 全部可追究（死页 73MB + IOSurface 78MB + CG Image 18MB 等）；阶段二凭 S0 归因数据推进，若实测证明 < 100MB 存在不可消除的构成项，以数据回评审重新定线（tech.md §6） |
| 启动方式 | **先评审本规格，再统一动工** | spec-first；P0–P5 一份规格 |
| GUI 进程模型 | **不在本规格范围**（见 §5 末条） | 若「悬浮条常驻 + 结果窗口按需进程」的拆分决策定案，另立规格承接其形态级改动；S4b 归因结论（tech.md §6.3）是该决策的输入，验收线 A5/A6/A6b 不因进程模型而变 |
| 行为契约 | 对外协议（消息/CLI/status 语义）不变 | 条目数显示改为近似值见 tech.md §5 风险表 |

## 3. 验收标准

验收环境：本机实机（1.26M 条目规模）+ 隔离环境（`HOME=/tmp/mce-dev`）。全部以 phys_footprint 计（`footprint <pid>` / 活动监视器）。

| # | 指标 | 验收线 |
| --- | --- | --- |
| A1 | daemon 稳态 footprint（运行 24h 后） | **≤ 100MB**（目标 60MB） |
| A2 | 单次全量重扫瞬时峰值 | 两档：S2（峰值瘦身）后 ≤ 450MB；S3（mmap 化）后复核 ≤ 300MB。重扫结束后 10s 内回落 |
| A3 | 重扫振荡收敛 | 实机连续 24h，dropped 引发的全量重扫 ≤ 2 次 |
| A4 | 日志增速 | daemon.log 日增 < 1MB；永久失败目录零重复刷屏 |
| A5 | GUI 稳态 footprint | 阶段一 ≤ 150MB；阶段二 ≤ 100MB（凭 S0 归因推进，见 §2 决策表） |
| A6 | GUI 泄漏钉 | 完整结果窗口万级行持续滚动 10min，footprint 增量 < 20MB |
| A6b | GUI 峰值 | 峰值 ≤ 400MB（基线 1.7GB；T5 首测仍 2.4GB——fontique 固定枚举开销，见 tech.md §6.3 A6b 复测裁决；`system_fonts` 移除后复测） |
| A7 | 性能不回退 | `scripts/bench.sh` 五项基准劣化 ≤ 5% |
| A8 | 正确性 | `engine/tests/parity.rs` 对拍零差异（含双层索引扩展）；全量测试绿 |

## 4. 用户可见行为变化

1. 「条目数」显示（status / GUI 状态条）在增量窗口内为近似值，落盘后精确——措辞由精确值改为「约 N 条」（协议字段不变，值语义放宽，见 tech.md §5）。
2. 因权限无法展开的目录（如无完全磁盘访问权限时的 `.Trash`、照片图库）：**保持现状可见**（目录条目在、子树为空——与首扫语义一致），计入「缺口清单」（status 可见），不再无限重试刷日志；用户补授权限后**重启 daemon 即自动重新索引**（负缓存随进程清零，缺口清单提示此点）。
3. 被删除目录的残留条目在事件到达时即时清除（现依赖全量重扫兜底），搜索结果中已删路径消失更及时。
4. 搜索结果内容与排序无变化。字形显示有一处**已接受的退化**（tech.md §6.2.1，A6b 裁决）：覆盖集外的生僻字形显示为 tofu 方块（汉字/韩文/常用符号由内置字体覆盖），彩色 emoji 退为黑白（egui 内置 NotoEmoji）——换取 fontique 回退慢路径（单次查询固定 194MB 开销）的整体移除。

## 5. 非目标

- 不做索引文件格式压缩（名称池分片压缩等）：P3 方案已达标，压缩属第二余量。
- 不改查询语法、协议编解码、CLI 命令面。
- 不引入 FSEvents 之外的事件源（轮询兜底等）。
- **不预设 GUI < 100MB 不可达**：阶段一（确定性手段）目标 150MB；阶段二由 S0 归因数据决定——若存在实测确认的不可消除构成项（如 GL 兼容层的最低 drawable 池），携数据回评审重新定线，而非事前拍定下限。
- **GUI 进程模型（如悬浮条常驻 + 结果窗口按需进程的拆分）不在本规格**：此类形态级改动影响协议、启动编排与 GUI 架构，须单独立项评审。**归属口径**：本轮保留 GUI 治理全部两阶段（S4a 确定性手段 + S4b 归因驱动）——S0.3 的归因数据（峰值 malloc_history、IOSurface 逐个归属）是进程模型决策的输入，顺序上必须先归因再定形态；验收线 A5/A6/A6b 不因进程模型而变。进程模型定案后，其形态级内存影响由新规格评估，本规格归因结论作为其输入移交。
